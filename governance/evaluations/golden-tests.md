# Golden Test Sets

The golden test set is the ground truth for each AI feature. It is the most important artifact in the evaluation system — it defines what "correct" means for that feature.

---

## What Is a Golden Test?

A golden test is a human-verified input/output pair that represents the correct behavior of an AI feature. The golden set is:
- **Static until intentionally updated** — it is the stable benchmark
- **Human-labeled** — not generated by the model being evaluated
- **Representative** — covers the full distribution of expected inputs
- **Adversarial in places** — includes edge cases and near-misses

---

## Golden Test File Format

Each feature stores its golden set in `evaluations/<feature-slug>/golden-set.json`:

```json
{
  "feature": "feature-slug",

  "tests": [
    {
      "id": "GT-001",
      "category": "happy-path",
      "input": {
        "user_message": "...",
        "context": "...",
        "constraints": "..."
      },
      "expected_output": {
        "format": "...",
        "content_must_include": ["...", "..."],
        "content_must_not_include": ["...", "..."],
        "tone": "..."
      },

```

---

## Golden Test Categories

Every golden set should include examples from each category:

| Category | Description | Minimum Coverage |
|---------|-------------|-----------------|
| happy-path | Ideal, well-formed inputs | 30% |
| edge-case | Unusual but valid inputs | 20% |
| adversarial | Inputs designed to confuse or mislead | 15% |
| regression | Historical bugs that should not recur | 15% |
| distribution-boundary | Inputs at the edge of the feature's scope | 10% |
| multilingual | Non-English inputs (if applicable) | 10% |

---

## Minimum Golden Set Size

| Feature Complexity | Minimum Test Cases | Recommended |
|-------------------|-------------------|-------------|
| Simple (single-turn, narrow scope) | 30 | 50 |
| Medium (multi-turn or broad scope) | 50 | 100 |
| Complex (reasoning, retrieval, multi-step) | 100 | 200 |

## Golden Set Management Protocol

### Creating a Golden Set
1. Define the feature's scope and expected input distribution
2. Collect real or realistic synthetic examples covering all categories
3. Have 2+ humans independently label each example
4. Resolve disagreements per the protocol in `evaluations/criteria.md`
5. Store at `evaluations/<feature-slug>/golden-set.json`
6. Version 1.0.0

### Updating a Golden Set
Golden tests must NOT be updated to "fix" a failing score — that defeats the purpose.

**Valid reasons to update:**
- Feature scope changes (approved via PRD change)
- New edge case discovered in production
- Category coverage gap identified in retrospective
- Labeling error corrected

**Each update:**
- Increment the version (patch for additions, minor for changes, major for scope redefinition)
- Document what changed and why in `golden-set.json` changelog field
- Re-run the full calibration after update

### Retiring a Golden Set
When a feature is deprecated, move its golden set to `evaluations/archived/<feature-slug>/`. Do not delete — retired golden sets are organizational memory.


## Regression Protocol

If a test passes in one eval run and fails in a subsequent run:

1. The failure is a **regression** — log it immediately
2. Identify the change between runs: model version, prompt version, or context change
3. If cause is identified → fix and re-run
4. If cause is unknown → escalate to analytics-agent + ALERT-001 review
5. Add the regression case to the `regression` category of the golden set if not already present
